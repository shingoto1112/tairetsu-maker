# 操作中の名前表示 A/B 測定（2026-10-06）

> **決定（2026-10-06、利用者）**: 測定では CPU 4倍の合成条件で名前常時表示に遅れの増加が見られたが、実機（13インチ iPad）は大幅に速く、利用者は「いつも名前を出す」を選んだ。StageCanvas の 120人以上での名前隠しは撤廃し、メンバー DOM の memo 化（位置等が変わらないメンバーは再描画しない）は残した。旧版との比較用の生データ（baseline・label-memo の CSV/MD、trace の JSON）はコミットしていない。

判定: **合格を確認できず、名前常時表示の採用を停止**。ステージ 6/6 条件、パレード 6/6 条件。各 A/B 3回、各条件にウォームアップ。
最大増加: rAF p95 33.40ms、定常 p95 33.20ms、33.3ms超 13.29ポイント、pointer→次rAF p95 14.90ms。Bの代理遅延p95最大 194.20ms。

## 方法・限界

- B は名前 DOM の memo 化、メンバー DOM 全体の memo 化、最新の確定状態へ委譲する安定したハンドラー、名前分割・文字色計算の再利用を含む候補ビルド。通常の作業ツリーでは既存の名前隠しを維持しており、測定ビルドだけで解除した。軽量化は残したが、常時表示を承認した状態ではない。
- 前回の測定と名前部分だけの memo 化も不合格（生データは未コミット）。今回はステージの単体ドラッグ2条件だけが相対基準を満たし、複数ドラッグ・パンの4条件が満たさなかった。
- **測定の変動が大きい**。ParadeCanvas は A/B で同じ実装なのに、200人の単体ドラッグで p95 が183.30→349.90ms、代理遅延が121.30→299.60msと変動した。名前描画だけが差の原因とは断定できない。前回 trace の B では測定用 tick 自身が584.23msを占めたため、trace も原因を特定するには不十分。合格の根拠には使わない。
- 作業中に別の割当UI変更が同じツリーへ追加された。今回のビルドは生成後に固定して測定したが、A/B生成間の全ソース一致は記録していない。今後の再現用スクリプトは両ビルドで同じソーススナップショットを使い、ハッシュを出力する。今回は確認量を増やさず再測定しない。
- パンは既に親の scrollLeft/scrollTop を操作している。親 transform 化はスクロール・慣性・目盛り・選択座標へ影響するため、この結果だけで変更しない。次の選択肢は測定器の負荷を減らして固定環境で再評価、iPad実機で評価、または許容基準を利用者と相談すること。名前隠しを黙って再導入したものではない。

- npm の既存 Vite/Playwright のみ。envFile:false の production build。Aはb5f4076の名前隠し、Bは作業ツリーの名前常時表示。空いているloopbackポートでpreview。架空データ・隔離コンテキスト・外部リクエスト遮断。ビルドはOS一時フォルダに作成し終了時に削除。
- 200/300人、1376×1032、CDP CPU 4倍、倍率150%。座標と配置は各A/B同一。単体・2人選択ドラッグはCDP mouse、パンはCDP touch。約16.67ms間隔で60点の同じ往復経路（1秒）。A/Bを試行ごとに交互に実行。
- Chromiumで入力が統合されるため、実際のpointermove受信期間の最初20%を開始、次70%を定常、最後10%＋120msを終了として分類。rAF間隔とtrusted pointermove受信→次rAFを採取。後者は入力から画面表示までの実遅延ではなく代理値。long taskはPerformanceObserver。OS/IPCの入力送信時間は代理遅延に含まれない。
- 表のp95/割合は各3試行の中央値。long task件数・合計は3試行の総和、最大は最大値。全指標と開始/定常/終了の表は [CSV](member-label-ab-summary.csv)。
- 合格基準はp95差≤2ms、33.3ms超の増加≤2ポイント、代理p95差≤8ms。Bで100ms以上が2試行以上に新規反復する条件がないこと。定常p95にも同じ基準を適用。絶対50msは目標として別記。Chromiumの合成負荷でありiPad実機の合格を保証しない。
